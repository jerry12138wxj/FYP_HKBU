## 5. 口径脚注（引用本表必须一并声明）

| 项 | 本表取值 | 说明 |
|---|---|---|
| 指标 | **museval BSSEval v4** 的 SDR | `compute_permutation=False`；与 museval 官方口径一致 |
| 声道 | **单声道**（`mean(axis=-1)`） | 四轨模型仍以立体声输入，评测前降为 mono |
| 数据集 / 子集 | **MUSDB18-HQ `train`** | 🔴 主表跑在 **`train`** 子集（`model_runs.json` 每条记录的 `subset` 字段可核），即**训练集本身** → 属 **in-domain 口径，数字偏乐观**；副表 §4 为 `test` 集 |
| 片段 | 3 个**能量均衡**片段 × 10 s | 每轨占比 14~43%；刻意避开「开头低频引子」类能量陷阱片段 |
| 聚合 | **中位数** | 先对窗取 `nanmedian`，再对 3 个片段取中位数（median-of-median） |
| **分析窗** | **window = 2 s / hop = 1.5 s**（88200 / 66150 样本） | 🔴 `evaluate()` **未传** `window`/`hop`，落到 museval 签名默认值；而多处脚本文档写的是「1 s 窗」，**与实现不符** |
| 窗宽影响（实测） | |Δ| 均值 **0.267 dB**、90 分位 **0.704 dB**、最大 **1.105 dB**（n=33 格，`metric_window_probe.json`） | 在 T3.1 选出的高能量片段上实测；按轨看 **bass 最敏感**（mean -0.296 dB），other 最稳（mean -0.011 dB） |
| 基线 | **mixture**（-5.30 dB，四轨均值） | 基线行在 §1 顶部；模型相对基线的增益才是可读结论 |
| RTF | 推理秒数 ÷ 音频秒数 | **受机器负载影响**，本机为 RTX 4070 Laptop 8 GiB 单卡；同一模型两次可差 2×，只做量级参考 |
| FLOPs | `FlopCounterMode`，**口径 = 2×MACs** | ⚠️ 只统计 torch 调度的算子，**`torch.stft` 与融合注意力不计入 → 是下界**；跨架构比较须配合实测时延 |
| Size | `sum(p.numel())`，取模型实例 | 非配置文件声明值；多 ckpt 模型为**合计** |

> 🔴 **两处必须主动交代的口径缺陷**（不要等被问）：
> 1. **主表在 `train` 子集上**：MUSDB18 train 正是多数对比模型的训练集 → 属 in-domain，数值系统性偏乐观；与参考表（`test`）差得远，**这不是实现错误而是口径差异**。
> 2. **实际窗宽 2 s / hop 1.5 s，不是文档写的 1 s**：已量化为 |Δ| 均值 0.267 dB（见上表）。若要与其他论文对齐，需把 `evaluate()` 补上 `window=44100, hop=44100` 后整表重跑。

> **三条通用差异**：① **子集不同**（本表 train / 参考表 test）；② **实现版本不同**（HTDemucs vs Demucs v1；自训 DPRNN vs 官方权重）；③ **评价口径不同**（mono、2 s 窗、3 均衡片段中位数 vs 参考表的整曲/其他池）。
>
> **答辩一句话**：「本表是同任务、同数据集族、**本机复现口径**下的实测结果；与参考表的数值差异来自实现版本与评价片段选择，逐格对齐需要原版 Demucs(v1) 与官方 DPRNN 权重，成本高、收益低 —— 我们选择把差异写清楚而不是硬凑数字。」
